DESARROLLO — MÓDULO AUDITORÍA BIM

Necesito desarrollar el Módulo Auditoría de la plataforma.

IMPORTANTE:
No utilizar nombres comerciales provisorios para la plataforma.
El nombre visible del módulo será simplemente:

AUDITORÍA

La aplicación trabaja sobre modelos Autodesk Revit / Forma / ACC mediante la infraestructura Autodesk disponible en el proyecto.

Este desarrollo debe integrarse a la arquitectura visual, componentes, autenticación, Autodesk Connector, Viewer, proyecto seleccionado y navegación ya existentes en la aplicación.

No crear una aplicación paralela.

========================================================
1. OBJETIVO GENERAL
========================================================

El módulo AUDITORÍA debe revisar la calidad tridimensional, técnica y posteriormente la calidad de datos de modelos BIM.

La lógica general será:

MODELO / VISTA
    ↓
CONFIGURACIÓN DE AUDITORÍA
    ↓
AUDITORÍA TRIDIMENSIONAL Y TÉCNICA
    ↓
HALLAZGOS
    ↓
VISUALIZACIÓN / EVIDENCIA
    ↓
POSIBLE GENERACIÓN DE INCIDENCIA
    ↓
AUDITORÍA DE DATOS EN ETAPA POSTERIOR

El módulo debe trabajar inicialmente sobre una auditoría independiente.

Las comparaciones:

- modelo vs modelo;
- especialidad vs especialidad;
- versión vs versión;

serán procesos posteriores que consuman los resultados de auditorías individuales.

========================================================

La unidad de auditoría será:

Proyecto

========================================================
4. ESTADOS DE RESULTADO
========================================================

Implementar exactamente los siguientes estados:

PASS
WARNING
FAIL
NOT EVALUATED
N/A
INFORMATION

Interpretación:

PASS
Cumplimiento verificable.

WARNING
Anomalía, desviación o mala práctica que requiere revisión.

FAIL
Incumplimiento verificable respecto de una regla activa.

NOT EVALUATED
No existen antecedentes, datos o configuración suficiente para ejecutar la regla.

N/A
La regla no es aplicable a esa población.

INFORMATION
Dato contextual o inventario; no afecta indicadores de calidad.

IMPORTANTE:

INFORMATION, NOT EVALUATED y N/A
no deben penalizar los porcentajes de conformidad.

========================================================
5. ARQUITECTURA DE CONOCIMIENTO
========================================================

Las reglas deben soportar tres niveles jerárquicos.

NIVEL 1
REGLAS MAESTRAS

Reglas objetivas comunes de la plataforma.

NIVEL 2
BUENAS PRÁCTICAS

Buenas prácticas generales y por especialidad:

- estructura;
- arquitectura;
- MEP;
- otras futuras.

Normalmente generan PASS o WARNING.

NIVEL 3
CATÁLOGO EMPRESA / PROYECTO

Permite almacenar reglas particulares:

- nomenclaturas;
- equivalencias;
- parámetros;
- familias;
- tolerancias;
- excepciones;
- criterios internos;
- clasificaciones.

Jerarquía:

GLOBAL
    ↓
EMPRESA
    ↓
PROYECTO

Cuando algo específico de empresa o proyecto no exista:

"Por Configurar"

========================================================
23. CRITERIO FINAL
========================================================

El objetivo NO es construir simplemente un "Model Checker".

El módulo debe convertirse en un motor configurable de auditoría BIM.

Debe poder responder:

¿Qué se auditó?
¿Qué reglas se utilizaron?
¿Qué pudo evaluarse?
¿Qué no pudo evaluarse?
¿Qué está correcto?
¿Qué requiere revisión?
¿Qué está objetivamente incorrecto?
¿Qué elementos están afectados?
¿Qué evidencia respalda el resultado?
¿Qué tolerancia se utilizó?
¿Qué regla corporativa se aplicó?

Y todo resultado debe poder navegar desde:

RESUMEN
→ CAPÍTULO
→ REGLA
→ HALLAZGO
→ ELEMENTO
→ VIEWER

Desarrollar la estructura de manera modular y reutilizable, evitando lógica específica acoplada a una sola especialidad o proyecto.
